# 📝→🎨 Kotoe（言絵）

> **「言葉だけで、その画像をどこまで再現できる？」**
> アプリ名は「**言葉（こと）＋絵（え）**」＝**言葉から絵へ**の変換そのものを表す。
> 投稿された画像をユーザーが言語化（テキストで描写）し、その説明文だけを頼りに AI が画像を生成。
> 元画像をどれだけ再現できたかを競う、**言語化スキルのゲーム兼検証アプリ**です。

---

## 🎯 コンセプト

「言葉による画像の描写は、どこまで正確に元画像を再現できるのか？」を体験・検証できるアプリ。

1. ユーザーが **お題画像** を投稿する
2. 別のユーザー（または投稿者）が、その画像を **言葉だけで描写** する
3. その描写文を AI 画像生成に渡し、**再現画像** を生成する
4. 元画像と再現画像を並べ、**再現度** を評価する
   - 他ユーザーによる **再現いいね**（主観評価）
   - **自動類似度スコア**（CLIP 等による客観評価）※拡張
5. 再現度ランキングで、**もっとも言語化が上手いユーザー** を可視化する

> ✅ **採用する設計：ユーザー（人間）が描写を書く版。** ゲーム性（ランキング・再現いいね）はこの設計が前提です。
> AI が自動で描写する案は不採用（観察ツール寄りになりゲーム性が失われるため）。ただし「人間 vs AI 対決」として一部取り込む拡張は検討（後述）。

## 💡 背景・着想

2つの問題意識を結びつけたところから着想しています。

1. **「日常にあるものを、言葉で正しく表現するとはどういうことか」** という普遍的な問い。私たちは見たものを毎日言葉にしているが、その描写が本当に正確かを確かめる機会は少ない。
2. **生成AIのプロンプトを実務で書く人が増えている** という現実。「意図した画像を言葉で引き出す力」は、いまや具体的な職能になりつつある。

この2つは「**画像を言葉でどれだけ正確に表現できるか**」という一点で結びつく。本サービスは、その描写力を **AIによる再現** で可視化し、楽しみながら鍛えられる場として実現することを目指す。単なるゲームではなく、**実務で価値を持つ「言語化／プロンプト記述」スキルの訓練・計測**という側面を持たせる。

## 🔍 先行事例と差別化

### 近い先行事例
- **ArtWhisperer**（スタンフォードの研究ゲーム）：目標画像に近づくプロンプトを反復的に探す仕組み。コアは近いが、**運営が用意した固定画像**を使う研究用のデータ収集が目的。
- **「プロンプト当て」系**（Find The Prompt / Unprompted 等）：AI画像を見て元のプロンプトを当てる、日替わりパズル。**向きが逆**で画像生成の工程がない。
- **image-to-prompt ツール**：画像から復元用プロンプトを逆算する実用ツール。ゲーム性はない。

### 差別化ポイント
- **ユーザー投稿型（UGC）**：お題画像をユーザー自身が投稿。先行事例の固定画像と異なり、コンテンツがコミュニティ駆動で増え続ける双方向プラットフォーム。
- **ソーシャル/競争レイヤー**：ランキング・再現いいね・お気に入りで「**描写が上手い人**」を可視化。先行事例にはない。
- **「言語化スキル」のフレーミング**：プロンプト工学ではなく「言葉で正確に描写する力」に焦点。実務（生成AIのプロンプト記述）にも通じる位置づけ。
- **日本語圏**：先行事例はほぼ英語。日本語で言語化を競う場は空いている。
- **差別化を設計で尖らせる案**：「1回の描写で勝負（反復しない）」「モデル向けキーワード禁止・自然文のみ」といった制約で、プロンプト芸ではなく純粋な描写力のゲームにできる。

## ✨ 主な機能

### 認証
- アカウント新規作成 / ログイン / ログアウト
- マイページ（自分の投稿・挑戦・**下書き（保存したプロンプト）**・お気に入り一覧）

### コア機能
- **画像投稿機能**：お題となる画像をアップロード（Cloudinary 保存）
- **言語化（描写）機能**：お題画像に対してテキストで描写を入力。「保存」（下書き）と「画像を生成」の2ボタンを用意。**「保存」したプロンプトは下書き（status: draft）として残り、マイページの「下書き」タブから後で確認・編集・生成できる**
- **画像生成機能**：描写文を画像生成 API に渡して再現画像を生成（**非同期処理**）。**生成したら即公開**（プロンプト入力の実感を重視し、結果を見てから選ぶことはできない）
- **削除機能（論理削除）**：生成結果が気に入らなければ削除可能。物理削除ではなく `discarded_at` フラグによるソフトデリート（再現いいね・通報の参照を壊さない／モデレーション記録を残すため）。**ただし削除しても、その生成は1日の生成回数上限から戻さない**（無限リトライによるチェリーピッキングと API コスト暴発の防止）
- **比較ビュー**：元画像と再現画像を並列表示
- **再現いいね機能**：再現画像（=描写）の出来に他ユーザーが投票
- **お気に入り機能**：気に入った投稿/再現をストック

### 一覧・回遊
- **ランキング機能（全体）**：再現いいね数 / 類似度スコアによる、ユーザー・挑戦の全体ランキング
- **ベスト再現ランキング（お題ごと）**：各お題の挑戦を再現度順に並べ、上位（例：トップ3）を「このお題のベスト再現」として強調。MVP は**いいね数順**、CLIP 導入後は**類似度スコア順**に切り替え可能（「人気順／再現度順」の選択式）
- **検索機能**（ransack）
- **ページネーション**（kaminari）

### 運用・安全性（公開アプリとして必須）
- **コンテンツモデレーション**：投稿画像・生成画像の不適切コンテンツ検出
- **通報機能**：ユーザーによる不適切投稿の報告
- **生成回数制限（レートリミット）**：API コスト暴発の防止（ログインユーザー限定 + 1日あたり上限）

### あると良い拡張
- SNS シェア（X など）— ゲーム性と相性が良い
- 自動類似度スコア（CLIP 埋め込みのコサイン類似度）
- コメント機能

### 画像生成 API の選定（重要）

> ⚠️ **DALL·E 2 / 3 は 2026年5月に API から削除済み**のため選択不可。

| 候補 | 概算コスト | 特徴 |
|---|---|---|
| **OpenAI GPT Image 1 Mini** | $0.005〜/枚（Low品質） | **導入が最もラク・プロンプト追従性◎。個人開発の入口に推奨** |
| OpenAI GPT Image 2 | $0.005〜$0.21/枚 | 最新フラッグシップ。高品質だが高価 |
| Google Imagen 4 Fast | $0.02/枚 | 価格性能比◎。ただし Vertex AI のセットアップが必要 |
| Flux（Replicate / fal.ai 経由） | $0.008〜$0.04/枚 | 安価。ホスト型アグリゲーター経由 |

> 🔒 API キーは必ず **Rails サーバー側**に保持し、フロントエンドには絶対に出さないこと。

### 決定（issue 4-3・2026-08-04 時点の単価）

**`gpt-image-2` / `quality: low` / `1024x1024` / `output_format: webp` / `output_compression: 90`。**

`gpt-image-1` は 2026-10-23 に停止するため対象外。1024×1024 の実勢価格は次のとおりで、
**最新フラッグシップの gpt-image-2 の low が $0.006、最安の gpt-image-1-mini の low が $0.005** と
ほぼ同額になっている（当初の推奨「GPT Image 1 Mini の Low」を書いた時点とは状況が変わった）。

| モデル | low | medium | high | テキスト入力 |
|---|---|---|---|---|
| gpt-image-1-mini | $0.005 | $0.011 | $0.036 | $2/1M tokens |
| **gpt-image-2** | **$0.006** | $0.053 | $0.211 | $5/1M tokens |
| gpt-image-1.5 | $0.009 | $0.034 | $0.133 | $5/1M tokens |

Kotoe の面白さは「描写文にどれだけ忠実に再現されるか」なので、プロンプト追従性は商品価値そのもの。
差額 $0.001/枚 を払う価値があると判断した。描写文（最大1,000文字）のテキスト入力を含めて
**1枚あたり約 $0.011**、想定 5 人 × 3 回/日 × 30 日 ＝ 450 枚/月 で **約 $5/月**。

モデル・品質・出力形式・圧縮率は環境変数にせず定数（`Images::Generators::Openai`）で持つ。
コストと出力品質を左右する判断なので、変更が PR として履歴に残るべきものだから。

### 非同期処理の選定：Solid Queue（決定済み）

Sidekiq と比較した結果、**Solid Queue を採用する**（導入は issue 4-1）。

| | Sidekiq | Solid Queue |
|---|---|---|
| ジョブの保存先 | Redis（別インフラが必要） | PostgreSQL（追加インフラ不要） |
| 取得方式 | ブロッキング（即時） | ポーリング（〜1秒の遅延） |
| Render での実行 | **独立プロセスが前提 → 有料のワーカーサービスが必要** | Puma のプラグインとして Web プロセス内で動く → **無料枠に収まる** |

決め手は **Render の無料プランではバックグラウンドワーカーが別サービス扱いで有料になる**こと。Solid Queue なら Web サービス1つで完結し、Redis も不要。

画像生成は1回10〜60秒かかる長いジョブで、しかも1日の生成回数に上限をかけるため、Sidekiq の「即時取得」という強みは活きない（Solid Queue のポーリング遅延1秒は体感に出ない。フロントは元々ポーリングで完了を検知する設計）。

> ⚠️ Solid Queue はポーリング型（worker は 1 秒間隔）なので、ワーカーが生きている間 Neon にクエリを投げ続け、Neon のオートサスペンドを妨げる。この性質が無料枠の維持に直結するため、下の「無料枠の制約」を必ず読むこと。

## 💰 無料枠の制約（issue 4-1 で調査・2026-07-31 時点）

Kotoe が $0 で動いているのは、各サービスを個別に無料プランにしたからではなく、**Render と Neon が連動して寝るから**である。この連鎖を壊す変更（常駐プロセス、キープアライブ、有料化）は、意図しない形で跳ね返る。

### 無料が成立している仕組み

```
誰もアクセスしない
   ↓ 15分
Render 無料 Web がコンテナごと停止（Puma も fork された Solid Queue の supervisor も死ぬ）
   ↓
ポーリングが止まる
   ↓ 5分
Neon がオートサスペンド ← ここで課金対象の時間が止まる
```

**Solid Queue のポーリングが 1 秒でも続くと、Neon は 5 分の静寂を得られず永遠に起きたままになる。** ジョブが 1 件も無くても同じ。

### 各プラットフォームの実数値

| | 上限 | 24時間稼働での消費 | 超過したとき |
|---|---|---|---|
| **Neon**（無料） | 100 CU-hours/月・プロジェクト | 730h × 0.25 CU = **182.5** | **compute がサスペンド**。既存接続は切断され新規接続も不可。次の請求期間まで復旧しない |
| **Neon ストレージ** | 0.5 GB（PITR 履歴は別枠で 6時間・1 GB-month） | — | **INSERT / UPDATE / DELETE が失敗**。データは消えないが、削除して空けることもできない |
| **Render**（無料 Web） | 750 instance-hours/月・ワークスペース | **730h** | 全 Free Web サービスを月末まで停止 |

Neon の 100 CU-hours は最小 0.25 CU 換算で**連続稼働 400 時間 ＝ 16.7 日分**。常時起動にすると**月の 17 日目で枠が尽き、残り 13 日はアプリが落ちる**。

### Render 無料枠のメモリ実測（issue 4-2 で計測・2026-08-03 時点）

512 MB は**コンテナ全体**（Puma ＋ Solid Queue の supervisor / dispatcher / worker / scheduler）で分け合う。
無料プランは Metrics が見られずシェルも使えないため、`GET /api/health` が返す値
（`Diagnostics::Memory`。cgroup から読む）で測った。**ダミー画像（15 KB の PNG）での値**である。

| | 使用量 | 増分 | 512 MB に対して |
|---|---|---|---|
| 起動直後（ジョブ未実行） | 362 MB | — | 71% |
| 生成 1 回目の直後 | 451 MB | **+89 MB** | 88% |
| 生成 2 回目の直後 | **475 MB** | +24 MB | **93%** |

内訳（2 回目の直後）：Puma 172 / worker 146 / dispatcher 135 / supervisor 134 / scheduler 133 MB。
ただし Solid Queue の 4 プロセスは Puma からの fork なので、**この RSS は共有ページを二重に数えている**
（合計は 720 MB になるが実使用は 475 MB）。

**1 回目の増分が大きく 2 回目が小さいのは copy-on-write の解消による。** fork 直後は Puma とページを
共有しており、worker がジョブを実行してそこに書き込むと共有が解けて専有ページになる。だから
「プロセスの RSS はあまり増えていないのに cgroup の anon が増える」という見え方になる。
共有解除は一度きりなので増分は逓減するが、**2 回目でも +24 MB あり頭打ちにはなっていない**。

**結論：収まってはいるが余裕は 37 MB しかない。** これはダミー画像での値で、4-3 で本物の画像生成 API を
載せると数 MB の画像データをメモリに持つことになる。**4-3 に着手する前にこの節を読むこと。**
削減の候補（着手時に計測して選ぶ）：

- `config/queue.yml` の `workers.threads` は 3。生成は 1 ユーザー 1 日 3 回が上限で同時実行の必要が薄いため、
  1 に下げれば worker のメモリを削れる可能性がある
- `RAILS_MAX_THREADS`（現在 3）を下げる
- ~~画像データをメモリに載せず Cloudinary へ渡す（生成 API が URL を返すなら、その URL を
  Cloudinary に取り込ませる経路が使える）~~
  → **成立しない**（issue 4-3 で判明）。gpt-image 系は **base64（`b64_json`）でしか画像を
  返さず**、URL 受け取りに対応していない。画像は必ず Ruby のヒープを通り、しかも
  「レスポンス本文 → JSON.parse → Base64.decode64 → Cloudinary の multipart 本文」で
  **瞬間ピークは画像サイズの約4倍**になる。代わりに **`output_format: webp` /
  `output_compression: 90`** でデータ量そのものを落とし、ピークを PNG の 5〜7 MB から
  1〜2 MB にした
- 有料ワーカーへの切り出し。ただし下の試算のとおり**実質 $26/月**になる

### Cloudinary の無料枠の数え方（issue 4-3 で調査・2026-08-04 時点）

25 クレジット/月。**1 クレジット ＝ 変換1,000回 ＝ ストレージ1GB ＝ 帯域1GB** で、
3つの用途に好きな配分で使える。

- **変換は「派生アセットが初めて作られたとき」に1回だけ**数えられる。同じ変換URLへの
  2回目以降のアクセスは加算されない（CDN から配信される）
- 変換と帯域は毎月リセットされるが、**ストレージだけは在庫で積み上がる**

450枚/月・12ヶ月時点の試算（1枚を10回閲覧と仮定）：

| | WebP(90) 0.3 MB/枚 | PNG 1.5 MB/枚 |
|---|---|---|
| ストレージ（累積 1.6 GB / 8.1 GB） | 1.6 | 8.1 |
| 帯域 | 1.35 | 6.75 |
| ダウンロード用 `f_png` 変換 | 0.45 | 0（不要） |
| **合計（クレジット/月）** | **約 3.4 / 25** | **約 15 / 25** |

**「PNG で保存して変換を避ければ安い」は成り立たない。** 一覧のサムネイルや比較ビューでは
どちらの保存形式でも変換（`f_auto,q_auto` 等）を使うため、変換の発生は形式に依存しない。
枠を先に食うのは変換ではなくストレージと帯域で、そこは WebP が5倍有利である。

### やってはいけないこと：キープアライブ

「コールドスタート（約1分）を消したい」という動機で外部から定期アクセス（GAS、cron-job.org 等）を仕掛けると、**逆効果になる**。

| | コールドスタート | 月のダウンタイム |
|---|---|---|
| 何もしない | 初回アクセスに約1分 | **0日** |
| キープアライブする | 無し（17日目まで） | **約13日** |

Render 側は 730 < 750 で辛うじて収まるが、**先に Neon が落ちる**。1 分の待ちを消すために 13 日の停止を買うことになる。同じ理由で **cron・外形監視・常駐ワーカーもすべて同じ結果**になる。

### 有料化した場合の実際の総額

有料プランの本質は「**スリープしなくなる**」こと。つまり上の連鎖が切れるので、Render だけ払っても Neon が落ちる。

| 構成 | 月額 | 結果 |
|---|---|---|
| 現状 | **$0** | コールドスタートあり。それ以外は正常 |
| Render のみ有料 | $7 | **17日目以降ダウン**。実質使えない |
| Render + Neon 有料 | $7 + 約$19 ≒ **$26** | 常時起動 |

Render のワークスペースは Hobby（$0）のまま有料インスタンスを置けるため、追加費用はインスタンス代のみ。Neon Launch は $0.106/CU-hour で、182.5 CU-hours ≒ $19/月。

### DB を Neon 以外に移す場合

コードは `ENV["DATABASE_URL"]` を読むだけで、Neon 固有の記述は無い（コメントのみ）。移行は環境変数の差し替えと `pg_dump` / `pg_restore` で済み、**アプリのコードは変わらない**。

| | ストレージ | 常時起動 | 期限 | 落とし穴 |
|---|---|---|---|---|
| **Neon**（現状） | 0.5 GB | 5分でサスペンド（**無効化不可**） | 無し | 100 CU-hours/月 |
| Render Postgres | 1 GB | 常時起動 | **30日で失効** | 失効後14日で**データごと削除**。本番には使えない |
| **Supabase** | 0.5 GB | 常時起動 | 無し | 7日間**無活動**で一時停止（Solid Queue のポーリングがある Kotoe では該当しない） |
| Aiven | 5 GB | 非アクティブで電源断 | 無し | バックアップ保持ゼロ・PITR 無し |
| Railway | — | 常時起動 | 初回クレジットのみ | 実質有料（$5/月〜） |

→ **将来「常時起動が必要」となった場合、Supabase 無料 + Render Starter $7 が有力**（$26 → $7）。ただし RAM 500MB 共有の固定リソースになり、Neon のオートスケールは失う。**今は移す必要がない**（常駐が必要になった時点で、その必要性とセットで判断する。移行コストは今やっても後でやっても同じ）。

### ストレージ 0.5 GB は律速にならない

**画像は Cloudinary にあり、Postgres に入るのは URL 文字列だけ**なので、行は小さい（実測）。

| データ | サイズ |
|---|---|
| 描写文（日本語146文字） | 438 bytes |
| Cloudinary の URL | 109 bytes |
| public_id | 43 bytes |

インデックス込みの 1 行あたりは `attempts` ≒ 1 KB / `posts` ≒ 0.5 KB / `likes`・`favorites` ≒ 0.1 KB。空の状態で 0.77 MB なので、**0.5 GB は挑戦 50万件に相当する**。

50万回の画像生成は API 費用だけで約 $2,500（GPT Image 1 Mini の $0.005/枚）。**Cloudinary の枠と生成予算を桁違いに先に使い切る**ため、DB ストレージが先に問題になることはない。

唯一の注意点は `solid_queue_jobs`。生成ジョブの `arguments` に描写文が入るため 1 行 1 KB 程度になり、掃除が止まると本体と同じペースで増える。`config/recurring.yml` の毎時掃除で対処済みだが、**4-2 で本番にジョブを流し始めたら `SolidQueue::Job.count` が減っていることを一度確認する**こと。

> 実運用での CU-hours 消費とメモリ実測は 8-2b 以降／4-2 で行う。

## 🏗 アーキテクチャ

```
[ User ]
   │
   ▼
[ Next.js (Vercel) ]  ──── JWT ────▶  [ Rails API (Render) ]
                                          │
                          ┌───────────────┼────────────────┐
                          ▼               ▼                ▼
                   [ PostgreSQL ]   [ Cloudinary ]   [ 非同期ジョブ ]
                   (Neon)           (画像保存)        (Solid Queue)
                                                           │
                                                           ▼
                                                  [ 画像生成 API ]
```

### ⏱ 画像生成の非同期フロー（必須）

画像生成は数秒〜数十秒かかるため、**リクエストを同期で待たせない**設計が必須です。

```
1. ユーザーが「画像を生成」を押す（描写文は先に保存される）
2. Rails が Attempt(status: generating) を作成し、GenerateImageJob を enqueue
   ※生成回数（1日の上限）はこの時点で消費する
3. ジョブが画像生成 API を呼び出し → Cloudinary にアップロード
   → (拡張) CLIP 類似度を計算 → Attempt を更新(status: published) ＝ 即公開
   → 失敗時は status: failed（ユーザーは再試行可能）
4. フロントエンドがポーリング / SSE で完了を検知し、再現画像とスコアを表示
```

> ⚠️ Render の無料プランは 15 分アイドルでスリープするため、**コールドスタートの遅延（約1分）**を考慮すること。定期アクセスで起こし続ける対処は取らない（「無料枠の制約」参照。Neon の枠を焼き切り、かえって月の後半がダウンする）。

## 🗃 データモデル案（人間が描写する設計の場合）

```
User
  ├─ has_many :posts
  ├─ has_many :attempts
  ├─ has_many :likes
  └─ has_many :favorites

Post（お題画像）
  ├─ belongs_to :user
  ├─ image (Cloudinary)
  ├─ title
  └─ has_many :attempts

Attempt（再現挑戦）
  ├─ belongs_to :post
  ├─ belongs_to :user
  ├─ description       # ユーザーが書いた言語化テキスト
  ├─ generated_image   # 生成された再現画像 (Cloudinary)
  ├─ similarity_score  # (拡張) CLIP 類似度などの自動スコア
  ├─ status            # draft / generating / published(=完了・即公開) / failed
  ├─ discarded_at      # 論理削除（ソフトデリート）用のフラグ
  └─ has_many :likes

Like（再現いいね）
  ├─ belongs_to :attempt
  └─ belongs_to :user

Favorite（お気に入り）
  ├─ belongs_to :user
  └─ belongs_to :post  (または :attempt)
```

> ランキングは Like 数 / similarity_score を集計して算出（`status: published` かつ `discarded_at` が nil のものが対象）。

## 🧭 技術選定の理由（Next.js + Rails API）

本プロジェクトは Rails モノリス + Hotwire でも実装可能で、認証・非同期処理はむしろそちらの方が簡潔です。それを理解した上で、以下の目的から **あえて分離構成（Next.js + Rails API）** を選択しています。

- **end-to-end のオーナーシップを示す**：フロント・バック・デプロイまで一人で通して構築できることを示す（キャリアチェンジの文脈で有効）。
- **比較ビューの UX**：元画像と再現画像を並べる/重ねる体験など、クライアント状態を持つリッチな UI は React/Next.js が作りやすい。
- **React/Next.js の実務スキル獲得**：市場価値の高いフロント技術を実装で身につける。

### 引き受けたトレードオフ（実装で対処する課題）
- **別ドメイン間の認証**：Vercel ↔ Render はクロスオリジンのため、JWT を Authorization ヘッダで送る方式で対処（cookie 共有は使わない）。
- **非同期生成の完了検知**：Hotwire の Turbo Streams のような自動プッシュが無いため、ポーリング / SSE をフロントで実装。
- **その他**：CORS 設定、デプロイ2系統、フロント/バックの型の二重管理。

> 💡 「簡単な道があると知った上で、目的のために難所を選び、その代償を自分で処理した」——この検討・選定・対処の過程そのものが、面接での技術選定アピールの核になる。
