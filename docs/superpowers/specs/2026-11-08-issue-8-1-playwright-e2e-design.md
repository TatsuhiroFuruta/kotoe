- 依存：7-3c（描写・生成ポーリング）、7-4（比較ビュー）。背骨では 3-3 の次、8-2b の前
- 作成日：2026-11-08
- 前提：CLAUDE.md「テスト戦略」「動作確認・デプロイの進め方」「セキュリティ」
- 前提：`frontend/AGENTS.md`（Next 16 の API は型定義とコンパイル済み実装を直接読む）

## なぜやるか

MVP の定義は「本番で動く（デプロイ済み）＋ コアループの E2E が green」（CLAUDE.md）。8-1 はその後半で、
8-2b（本番の最終疎通）が依存している。

E2E が守るのは、RSpec と Vitest では原理的に見えない**フロントとバックのつなぎ目**（CORS・JWT・
生成ポーリング）。特に 7-1・7-2 の申し送りには、**今まで手動確認しか無く、自動テストが 1 件も無い箇所**が
含まれている（backlog 8-1 のタスク欄）。7-1 では実際に、ガード付きページを直接ロードしたときだけ
`/login` へ飛ばされるバグを埋め込んでいる。

## 目標

1. **E2E①（認証フロー）** と **E2E②（コアループ）** の 2 本が、ローカルと CI の両方で green になる
2. backlog 8-1 の申し送り（下の「シナリオ」）をすべて含む
3. PR ごとに CI で自動実行され、つなぎ目が壊れたら PR が赤くなる

## 目標でないもの

| 項目 | 理由 |
|---|---|
| 本番・プレビューに向けて流す | ユーザーの判断（2026-11-08）。本番ではテストのユーザー・お題が溜まり、画像生成が本物（OpenAI）になり実費がかかる。8-2b の最終確認は今までどおり手で行う |
| 網羅的な画面テスト | CLAUDE.md「テスト戦略」：E2E は少数精鋭。網羅よりつなぎ目 |
| 複数ブラウザ・スマホの表示崩れの検出 | 同上。私の判断：Chromium のデスクトップ幅 1 本 |
| React Testing Library などのコンポーネントテスト | CLAUDE.md で見送り済み |
| 本物の画像生成 API | ダミー（`KOTOE_IMAGE_PROVIDER` の既定。本番以外は `dummy`）で通す |

## やってはいけないこと（技術的に通っても失敗とみなす）

- **本番（Render・Vercel・Neon・Cloudinary の `kotoe/production/`）に 1 件でも書き込むこと**
- **開発 DB（`kotoe_development`）や Cloudinary の `kotoe/development/` を汚すこと**。E2E のデータは専用の場所にだけ置く
- **秘密を repo・ログ・テストの成果物（trace・スクリーンショット）に出すこと**。Cloudinary のキーは GitHub の Secrets
  とローカルの git 管理外のファイルにだけ置く（CLAUDE.md「セキュリティ」、メモ：env の本文を表示しない）
- **待ち時間を固定の sleep で合わせること**。たまたまの失敗（flaky）の元になる。画面の状態を待つ
- **アプリの本体に E2E のためだけの近道（認証の抜け道、テスト用の公開 API など）を足すこと**。足す必要が
  出たら、作る前に相談する

## 決まったこと

### ユーザーが決めたこと（2026-11-08）

1. **ローカルと、PR ごとの CI の両方で回す。** CI では rubocop・rspec と並ぶ別のジョブにする
2. **ローカルは E2E 専用の DB を毎回作り直す。** 開発中の `docker compose up` のデータと混ぜない。生成の上限
   （1 人 1 日 3 回、全体 1 日 50 回。`lib/attempts/generation.rb`）に開発データが影響しないようにするため
3. **Cloudinary は本物を使う。** 画像の保存先は本番・開発と分ける（下の決定 7）
4. **本番・プレビューには流さない**

背景として確認した数字（ユーザーと共有済み）：Cloudinary 無料枠は月 25 クレジット（1 クレジット＝変換 1,000 回・
保存 1GB・配信 1GB のいずれか）。E2E を CI で月 100 回回した見込みは、変換で約 1 クレジット、配信で約 0.02、
保存は 1 年で約 0.12。**Cloudinary のアカウントは本番と共有している**ので、CI の分は本番の枠から減る。
GitHub Actions は public リポジトリなので無料・時間の上限なし。

### 私の判断（ビルダーが変えてよいが、変えるなら理由を残す）

5. **CI は Docker を使わず、今の `ci.yml` と同じく Ruby・Node を直接用意する。** 既存ジョブと同じキャッシュ
   （`bundler-cache`・`cache: npm`）が効き、Postgres はサービスコンテナで足りる
6. **Chromium のデスクトップ幅だけ**
7. **E2E の画像は Cloudinary の専用フォルダに入れる。** 今の保存先は `kotoe/#{Rails.env}/posts|generated`
   （`lib/images/uploader.rb`）。ローカルの E2E を `RAILS_ENV=development` のまま動かすと `kotoe/development/` に混ざり、
   `RAILS_ENV=test` はジョブのアダプタが `:test`（`config/environments/test.rb`）でジョブが実行されない。
   **専用フォルダ（例：`kotoe/e2e/`）に入れる手段はビルダーに任せる**（フォルダの接頭辞を環境変数で上書きできる
   ようにする、など）。条件：既定の挙動（未設定なら `kotoe/#{Rails.env}`）を変えないこと。本番は触らないこと
8. **テストの後片付け**：E2E 専用フォルダの画像を、実行の最後に Cloudinary から直接消す（任意。入れるなら
   `kotoe/e2e/` の下だけを対象にし、それ以外の接頭辞を消せない作りにする）。アプリの削除機能（論理削除）は
   使わない。E2E の DB は毎回作り直すので、消した画像を参照する行が残らない。入れない場合でも保存の増加は
   1 年で約 120MB の見込み。
   **後片付けを入れるなら、保存先を実行ごとのサブフォルダ（例：`kotoe/e2e/<実行 ID>/`）に分け、自分の実行の
   フォルダだけを消す。** PR の CI・main への push・ローカルが同時に走ったとき、`kotoe/e2e/` 全体を消すと
   互いの画像を消し合い、たまたまの失敗の元になるため（レビューでの指摘）
9. **前提データは API で作り、検証したい流れだけを画面で操作する。** たとえば E2E② の「別ユーザーのお題」は
   API（`POST /api/auth/sign_up`・`POST /api/posts`）で用意する。テストの速さと安定のため。
   公開されている API を使うだけなので、アプリ本体に近道は足さない。
   - 呼ぶのはアプリのフロントではなく **Playwright のテストコード**（ブラウザを開かずに HTTP を送る `request` の仕組み）。
     「ユーザーを作る」「お題を投稿する」といった準備の関数は、E2E 用の補助ファイル（例：`frontend/e2e/support/` の下）に
     まとめ、テストごとに直接 `fetch` を散らさない。お題の画像は小さなテスト用の画像ファイルを E2E 側に置く。
     どれもアプリのビルドには含めない
   - 選ばなかった案：準備も画面で操作する（遅く、確かめたい流れと関係ないところで落ちる）。Rails の seed・FactoryBot・
     `rails runner` で DB に直接作る（テストを回す側に Ruby が要り、バリデーションと Cloudinary へのアップロードを飛ばす）。
     E2E 専用の API を Rails に足す（「やってはいけないこと」）
10. **ユーザーは実行ごとに新しく作る**（メールアドレスに乱数や時刻を含める）。1 人 1 日 3 回の生成上限に
    繰り返しの実行が当たらないようにするため
11. **バックエンドが落ちた状態（`unreachable`）は、プロセスを止める代わりに Playwright のネットワーク
    差し止め（`page.route` で API へのリクエストを `abort`）で作ってよい。** ローカルと CI で同じ方法が使え、
    サーバーの再起動を待たずに済む。ただし、実際にバックエンドを止めたときと画面の動きが同じになるかを
    **一度は実測で確かめる**（メモ：レビューで挙動の主張が割れたら実測）。違えば止める方法に変える
12. **失敗したときだけ trace・スクリーンショットを残し、CI では成果物としてアップロードする。**
    成果物にトークンが写り込みうる（trace はリクエストヘッダーと `localStorage` を含む）。テスト用の使い捨て
    ユーザーのトークンで、E2E の DB と一緒に捨てられるので許容する。**Cloudinary のキーは写らない**こと
    （ブラウザには渡らない。CLAUDE.md のとおりキーは Rails 側だけ）を確認する

## シナリオ

backlog 8-1 のタスク欄から写したもの。**太字の項目は、これまで自動テストが無かったもの。**

### E2E①：認証フロー

1. 登録 → ログイン → ログアウト
2. 未ログインでガード付きページ（例：`/mypage`、`/posts/new`）を開くと `/login?next=...` へ送られ、ログイン後に元のページへ戻る
3. **ログイン済みのまま、ガード付きページを直接ロード／リロードしても `/login` へ飛ばされない**
   （7-1 の申し送り。`<Link>` のクライアント遷移ではこの経路は露出しない。必ず `page.goto` か `page.reload` で開く）
4. **ログアウト後に同じトークンで認証付き API を叩くと 401 になり、フロントがトークンを自動で破棄する**
   （2-1 の denylist との結合点）
5. **`unreachable` からの復帰**（7-2 の申し送り。バックエンドに届かない状態でガード付きページをリロード）：
   - (a) `/login` へ飛ばされない
   - (b) ヘッダーとページの「再試行」で、バックエンドの復帰後にログイン状態へ戻る
   - (c) ヘッダーの「ログアウト」で、バックエンドに届かないままでも未ログインへ抜けられる
6. **`?next=` のオープンリダイレクト防御**：`/login?next=//evil.example` と `/login?next=%2F%09%2Fevil.example`
   でログインし、`/` に着地する

### E2E②：コアループ

ログイン → お題閲覧（一覧 → 詳細）→ 描写を書く → 「画像を生成」→ 生成ポーリングを経て即公開 →
比較ビュー（`/attempts/[id]`）で元画像と再現画像が並ぶ → **別のユーザーで**その挑戦にいいね（いいね数が増える）

- いいねは自分の挑戦にはできない（422 `cannot_like_own_attempt`）ので、ユーザーは 2 人要る
- 生成はダミーだが、**Solid Queue のジョブとして非同期に実行され、フロントがポーリングで公開を検知する**
  経路をそのまま通すこと（ここがつなぎ目）。ジョブを同期実行に差し替えない

## 実行環境

### ローカル

- 開発環境（`docker compose up` の `db`・`backend`・`worker`・`frontend`）と**並べて動かせる**こと、または少なくとも
  開発環境のデータを壊さないこと。ポートが衝突するなら E2E 用に別のポートを使う
- DB は E2E 専用（例：`kotoe_e2e`）で、**実行のたびに作り直す**
- ジョブを実行するワーカーが要る（`bin/jobs`、または Puma の `SOLID_QUEUE_IN_PUMA`）
- コマンド 1 本で、DB の作り直し → サーバー起動 → テスト → 後片付けまで進むこと。手順は README（ルート）の
  ローカル開発の節に足す
- ホストに Ruby が無くても回せること（今の開発は全部 Docker 越し）。Playwright 本体とブラウザをホストに入れるか
  コンテナで動かすかはビルダーに任せる。どちらにしても frontend のコンテナは Debian ベースのまま（メモ：alpine は不可）
- Cloudinary のキーは今の `backend/.env.development` と同じものを使ってよい（同じアカウント。保存先のフォルダだけ分ける）

### CI（GitHub Actions）

- `.github/workflows/ci.yml` に E2E のジョブを足す。既存の 3 ジョブと並列
- トリガーは既存と同じ（`pull_request` と `main` への `push`）
- Secrets：`CLOUDINARY_URL`（E2E 用。値は今と同じアカウントのもの）。**fork からの PR では Secrets が渡らない**ので、
  そのときの扱い（E2E ジョブを飛ばす、など）を決める。今の開発は本人だけなので、飛ばして構わない
- フロントの環境変数 `NEXT_PUBLIC_API_BASE_URL`（E2E 用の Rails の URL）と `NEXT_PUBLIC_CLOUDINARY_CLOUD_NAME`
  も E2E ジョブに渡す。後者は `frontend/src/lib/cloudinary.ts` が配信 URL を作るのに使い、`next build` の
  **ビルド時**に埋め込まれる。未設定だと比較ビューに画像が出ない。値は秘密ではない（クラウド名は配信 URL に
  そのまま出る）ので、Secrets でも Variables でもよい
- Rails 側の `CORS_ALLOWED_ORIGINS` は、E2E 用のフロントのオリジン（ポートを変えたならそのポート）に合わせる
- Next.js は本番ビルド（`next build` → `next start`）で動かすか `next dev` かはビルダーに任せる。
  本番ビルドのほうが本番に近く、ハイドレーションの経路（シナリオ 3）も本番と同じになる
