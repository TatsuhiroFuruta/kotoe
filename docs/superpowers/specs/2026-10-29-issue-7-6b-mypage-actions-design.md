## 決めたこと

### 決定 1：下書きカードのボタンは「続きを書く」と「削除」

ユーザーの決定（2026-10-29）。デザインブリーフ 7 は「生成する」「編集」「削除」の 3 つだが、7-6a 決定 2 で
「生成する」も「編集」も同じ画面（お題詳細の描写フォーム、文面入り）に移ると決まっている。行き先が同じ
ボタンを 2 つ並べず、「生成する」と書いてあるのに押しても生成されない、というずれも避ける。

- 「続きを書く」：`/posts/[post.id]?draft=<draft.id>` への `<Link>`。生成はその画面で「画像を生成」を押して行う
- 「削除」：確認ダイアログ（決定 5）を開く `<button>`
- **お題が削除済み（`post.discarded`）の下書きには「削除」だけを出す**（4-4 の申し送り。PATCH も generate も 404 になる）
- 2 つのボタンはカード下端の行に置く。カード自体はリンクにしない（7-6a 決定 6 のまま）

### 決定 2：受け口 `/posts/[id]?draft=<id>`

ユーザーの決定（2026-10-29）を含む。7-6a 決定 2 の具体化。

**URL の扱い**

- `parsePostDetailQuery` に `draft` を足す（正の整数だけ受け付け、それ以外は「指定なし」）。`page.tsx` から
  `PostDetail` → `AttemptComposer` へ渡す。`useSearchParams()` は使わない
- `postDetailHref` は今までどおり `sort` / `page` だけを組み立て、**`draft` は載せない**（並び替え・ページ送りの
  リンクで下書きが引き継がれないように）。受け口へのリンクは別の関数（例：`draftResumeHref(postId, draftId)`）で作る。
  どちらも `post-detail-query.ts` に置き、Vitest に足す（`test/lib/posts/post-detail-query.test.ts`）

**開けたとき**

- `GET /api/attempts/:draft` が成功し、`attempt.status === "draft"` かつ `post.id`（応答）が URL の `[id]` と一致し、
  `attempt.user.id` がログイン中のユーザーと一致する
- 描写フォームを `draftId` と文面（`text` と `savedText` の両方）を入れた状態にする。開いた直後は「保存済み」の状態
  （今の `isSaved` が真）
- そこで書き直して「保存」すると **同じ下書きへの PATCH**（新しい下書きは増えない）。「画像を生成」は同じ下書きから生成する
  （未保存の書き直しがあれば、今の作りどおり保存してから生成）
- 読み込み中は、フォームに入力させない（空のフォームに書き始めた直後に下書きの文面で上書きされるのを防ぐ）。
  見せ方は作り手に任せる（テキスト欄を無効にする、スケルトンにする、など）

**開けなかったとき**（ユーザーの決定）

- 対象：404（他人の下書き・削除済み・お題が削除済み・存在しない）、`status` が draft 以外（生成済み）、
  `post.id` の不一致（別のお題の下書き）、本人でない
- **すべて同じ扱い**：お題詳細は普通に表示し、描写フォームは空で開く。トースト（error）を 1 種類出す。
  文言の案：「この下書きは開けませんでした」。理由は出し分けない（他人の下書きの存在を漏らさない。API も 404 で隠している）
- **URL から `?draft=` を消す**（`router.replace`、`sort` / `page` は残す、スクロールさせない）。リロードで同じトーストを繰り返さないため
- 通信の失敗（timeout・通信断・5xx）は「開けなかった」とは分ける。文言は `toRequestErrorMessage` に任せ、
  `?draft=` は残す（リロードで再試行できる）。描写フォームは空で開く
**認証状態ごとの扱い**（私の判断。レビューで指摘された穴を埋めた）

| 認証状態 | 取得 | 画面 | `?draft=` |
|---|---|---|---|
| `loading` | 確定するまで待つ（取得しない） | フォームは入力させない | 残す |
| `authenticated` | 取得する。本人判定には `auth.user.id` を使う | 上の「開けた／開けなかった」 | 上のとおり |
| `unauthenticated` | 取得しない（下書きは本人にしか見えない） | 今の描写フォームと同じログイン導線。トーストは出さない | 残す |
| `unreachable` | 取得しない（`user` が無く本人判定できない） | 今の描写フォームの `unreachable` の扱いのまま。下書き用のトーストは出さない | 残す |

- 取得中に 401 が返ったとき（期限切れのトークン）：`api.ts` が失効の処理（トークンを捨て、7-2.6 のトーストを出す）を
  済ませる。受け口は「開けなかった」に**入れない**。下書き用のトーストを重ねず、`?draft=` も残す（ログインし直せば開ける）
- **ログイン導線の `next` に `draft` を載せる**。今の描写フォームのログインリンクは
  `/login?next=${postDetailHref(postId)}`（`attempt-composer.tsx:428`）で、このままだとログイン後に `draft` 無しで戻り、
  下書きが開けない。受け口から来たときは `next` を受け口の URL（`draftResumeHref`）にする。`sort` / `page` は引き継がない
  （受け口からのリンクは `sort` / `page` を持たないため）

**生成を始めたら**（私の判断）

- 受け口から開いた下書きで**生成が始まったら**、URL から `?draft=` を消す。「始まった」は、フォームが生成中
  （`phase` が `polling`）に入った時点とする。generate の 202 だけでなく、応答が不明なまま確かめに行く経路
  （`shouldConfirmGeneration`）や、保存が `attempt_not_draft` で既存の生成に合流する経路も含める。
  生成後のリロードで、生成済みの下書きを開こうとして「開けませんでした」が出るのを防ぐため

### 決定 3：削除できる場所は、マイページの 2 タブと挑戦詳細

ユーザーの決定（2026-10-29）。

| 場所 | 対象 | 置き方 |
|---|---|---|
| マイページ「下書き」 | 下書き | 決定 1 の行の「削除」 |
| マイページ「自分の挑戦」 | 公開済みの挑戦 | カード下端に、**リンクの外**に「削除」の行を足す。画像と本文は今までどおり挑戦詳細へのリンク（お題が削除済みのカードはリンク無しのまま）。今の `MyAttemptCard` は `<Link>` が `<article>` ごと包んでいるので、`<article>` の中に `<Link>`（画像と本文）とボタンの行を並べる形へ組み替える |
| 挑戦詳細 `/attempts/[id]` | 本人の公開済みの挑戦 | いいね・コピー・ダウンロードの行（`attempt-detail.tsx:120`）に「削除」を足す。`isOwner` のときだけ |

お題詳細の挑戦一覧・表彰台には置かない。デザインブリーフ 3-B と 7-3b の申し送りからは外れる。理由：

- `AttemptCard` はカード全体が `<a>` で、中にボタンを入れられない（押せる要素の入れ子は HTML の規則違反で、
  押すと削除メニューと同時に挑戦詳細へ移る）。組み替えると、共用している表彰台にも波及する
- 削除した挑戦がベスト 3 に入っていると、一覧と表彰台の両方を取り直す処理が要る
- 結果を見て消したくなる場面は、生成後に移る挑戦詳細で受けられる

### 決定 4：削除したあとの画面

- **マイページ**：一覧を取り直し、統計（`GET /api/me`。取得しているのは `ProfileHeader`）も取り直す（公開済みの挑戦を消すと挑戦数と獲得いいねが減るため。
  下書きのときは取り直さなくても値は変わらないが、分岐を足さずに同じく取り直してよい）。トースト（success）を出す
- **ページの最後の 1 枚を消したとき**（私の判断）：2 ページ目以降なら 1 つ前のページへ移る（`mypageHref`、`router.replace`）。
  1 ページ目なら取り直すだけ（空状態が出る）
- **挑戦詳細**：`/mypage?tab=attempts` へ移り（`router.replace`。「戻る」で消した挑戦の画面に戻らないように）、トースト（success）を出す
- 削除が 404 だったとき（別のタブで消した、など）：もう無いので、成功と同じ後処理をする。トーストの文言は作り手に任せる
- 通信の失敗：ダイアログを閉じずにエラーを出し、もう一度押せるようにする

### 決定 5：確認ダイアログ

- 3 か所で同じ部品を使う。ボタンは「やめる」「削除する」
- 文言（私の判断）：
  - 挑戦：「この挑戦を削除しますか？」＋「削除しても、今日の生成回数は戻りません」
  - 下書き：「この下書きを削除しますか？」（下書きはまだ生成回数を使っていないので、回数の注記は付けない）
- 送信中は「削除する」を押せなくする（二重送信の防止）
- 実装は作り手に任せる。ネイティブの `<dialog>`＋`showModal()`（フォーカスの閉じ込めと Esc を任せられる）を推奨。
  ブラウザの `confirm()` は使わない（Chrome 拡張での確認作業が止まるため。CLAUDE.md の運用とも合わない）
- 閉じたら、開いたボタンへフォーカスを戻す（そのボタンが消えたとき＝削除に成功したときは除く）

## 手動確認（ブラウザ）

- 下書きタブ →「続きを書く」→ 文面入りで開く → 書き直して保存 → マイページに戻ると、カードは 1 枚のまま文面だけが新しい
- 同じく開いて「画像を生成」→ 結果が出る → URL から `?draft=` が消えている → リロードしてもトーストが出ない
- 他人の下書き id・生成済みの id・別のお題の id・存在しない id を URL に手書き → 空のフォーム＋トースト、URL から `?draft=` が消える
- 未ログインで `?draft=` 付きの URL を直接開く → ログイン導線が出て、トーストは出ない → ログインすると受け口に戻り、文面入りで開く
- お題が削除済みの下書き：「削除」だけが出る。削除できる
- 自分の挑戦タブ・挑戦詳細から削除 → 確認ダイアログ → 消える／マイページへ移る、統計の挑戦数が減る
- 2 ページ目の最後の 1 枚を削除 → 1 ページ目に移る
- キーボードだけで：ダイアログが開く・Esc で閉じる・フォーカスが戻る
- **直接ロード**（`/posts/[id]?draft=<id>` をアドレスバーから）も必ず確かめる。Link 遷移だけだとハイドレーション経路を通らない（7-1 の教訓）
